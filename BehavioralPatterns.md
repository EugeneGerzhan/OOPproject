# Поведінкові шаблони в проєкті (структурований текст і гра)

Рефакторинг: вивід програми, команди та існуючі тести не змінилися. Нові можливості (команда `undo`)
додані поверх. Нижче: що саме застосовано, де і чому.

| Шаблон | Файли | Що дає |
| Visitor | `ITextVisitor`, `IText.Accept`, `TextDto`, `TextMapper` | Операції над документом винесені з елементів; немає `switch` за типами |
| Iterator | `Container.SelfAndDescendants()` | Єдиний обхід дерева замість чотирьох рекурсій |
| Memento | `TextMemento`, `UndoHistory`, `TextFactory.CreateMemento/Restore` | Знімки документа для скасування |
| Command | `ICommand`, `DelegateCommand`, `UndoableCommand`, `CommandInterpreter` | Команди як об'єкти, undo додається обгорткою |
| Template Method | `EntityDto` | Єдиний скелет `Render()` для DTO гри |
| Strategy (уже було) | `IAbility` | Здібності персонажа: взаємозамінні алгоритми |

## Visitor
**Що.** `IText.Accept<T>(ITextVisitor<T>)`; кожен елемент (`Root`, `Heading`, `Paragraph`) викликає метод відвідувача
для власного типу (подвійна диспетчеризація). Відвідувачі: `TextDto` (форматування) і `TextMapper.DataVisitor`
(перетворення в моделі даних).

**Чому.** Раніше кожна операція мала власний `switch` за типами елементів, тож новий вид елемента вимагав
шукати всі такі місця. Тепер нова операція це новий клас-відвідувач (елементи не змінюються), а новий вид
елемента додає метод в інтерфейс, і компілятор показує кожного відвідувача, якого треба оновити.

## Iterator
**Що.** `Container.SelfAndDescendants()` (метод-ітератор з `yield`) лениво обходить піддерево в глибину.

**Чому.** Пошук елемента за id, пошук батька, найбільший id (`TextFactory`) та підрахунок елементів при копіюванні
(`cp`) тепер прості LINQ-запити по одній послідовності. Структура зберігання дерева ховається. Це ідіоматична
для C# реалізація шаблону, тому окремі класи ітераторів були б зайвими.

## Memento
**Що.** `TextFactory` (originator) створює `TextMemento` (знімок документа і поточної позиції) та відновлює
його (`Restore`). `UndoHistory` (caretaker) зберігає знімки й не бачить їхнього вмісту: члени `TextMemento`
мають доступ `internal`.

**Чому.** Скасування потребує знімка стану без розкриття внутрішньої будови документа. Знімок складається з
незмінних даних, тож подальші зміни документа його не зачіпають.

## Command (+ Memento)
**Що.** `ICommand` з виконавцями `DelegateCommand` (обгортає звичайний метод) та `UndoableCommand` (обгортка,
яка до виконання бере знімок, а після залишає його в історії, лише якщо документ справді змінився:
`TextFactory.Revision`). Інвокер: `CommandInterpreter`. Клієнт: `TextCliHandler`. Отримувач: `TextFactory`.

**Чому.** Команди `add`, `rm`, `cp`, `load` стали скасовуваними без змін у їхній логіці: `undo` додається в
одному місці. Шаблон поєднаний з делегатами C#, тому існуючі обробники реєструються як і раніше.
Навігація (`cd`, `up`), друк і команди, що нічого не змінили (помилка, скасування користувачем), в історію не потрапляють.

## Template Method
**Що.** `EntityDto.Render()` фіксує скелет (коротко чи докладно), а `CharacterDto`, `ItemDto`, `AbilityDto`
реалізують кроки `ShortLine()` і `DetailLines()`.

**Чому.** Вибір між формами записаний один раз, і всі DTO гри поводяться однаково. Вивід не змінився.

## Strategy (вже було)
`IAbility` це взаємозамінні алгоритми дії персонажа (`RageAbility`, `FlurryOfBlowsAbility`, `CustomAbility`).
Додано лише коментар з поясненням.

## Що свідомо не застосовано
* **Observer.** У системі немає підписників на події; нова структура лише ускладнила б код.
* **Chain of Responsibility.** Команда завжди має відомого виконавця (таблиця команд), тому ланцюжок не потрібен.
* **State.** Стан персонажа (живий, захищається, переможений) визначається даними, і окремі класи станів
  дали б лише додатковий шар без нових поведінок.
* **Mediator.** Взаємодію персонажів уже веде `Game`, а в консольному режимі її роль виконує обробник команд.
* **Interpreter.** Розбір тексту команд уже виконує `CommandInterpreter`; повноцінна граматика не потрібна.
