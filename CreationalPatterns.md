# Генеративні шаблони в системі структурованого тексту

Система: `OOPTextProject/TextSystem` (Root → Heading → Paragraph, патерн Composite) та її використання
в консольному інтерфейсі (`SOLID`). Додано три генеративні шаблони.

| Шаблон           | Файли                                                                  | Що дає                                        | 
|                  |                                                                        |                                               |
| Abstract Factory | `Formatting/*`, `TextDto`                                              | Нові представлення документа без змін коду    |
| Builder          | `Building/DocumentBuilder`, `CharacterSheetBuilder`                    | Безпечне покрокове створення складного дерева |
| Prototype        | `IPrototype`, `Heading.CloneAs`, `TextFactory.AddCopy`, команда `cp`   | Глибоке копіювання піддерев                   |

## 1. Abstract Factory: представлення документа

**Що.** `ITextFormatFactory` створює родину форматерів: `IRootFormatter`, `IHeadingFormatter`,
`IParagraphFormatter`. Конкретні фабрики: `PlainTextFormatFactory`, `HtmlFormatFactory`,
`MarkdownFormatFactory`. Реєстр доступних форматів: `TextFormats`.

**Де.** `TextDto` (клієнт) обходить дерево й делегує подання кожного елемента форматерам вибраної
фабрики. Фабрику вибирає команда `print --format html|markdown|plain` та `sheet <персонаж> --format ...`.

**Чому.** Раніше `TextDto` мав єдиний жорстко заданий plain-формат, тож для HTML довелося б
переписувати клас або додавати гілки `if`. Фабрика гарантує, що всі елементи документа
подаються в одному форматі (корінь, заголовок і абзац створюються однією родиною).
Додавання нового формату (наприклад, TeX) це один новий клас + один рядок у `TextFormats.All`;
`TextDto`, `TextFactory` і консольні команди не змінюються (принцип відкритості/закритості).

**Відхилення від ідеї з методички.** Фабрика створює не самі елементи документа, а їх *представлення*.
Моделі лишаються чистими (без логіки відображення), як було зроблено на практичній про моделі та DTO.

**Відповідність ролям GoF.** AbstractFactory = `ITextFormatFactory`; ConcreteFactory = `*FormatFactory`;
AbstractProduct = `IRootFormatter`, `IHeadingFormatter`, `IParagraphFormatter`;
ConcreteProduct = вкладені приватні класи фабрик; Client = `TextDto`.

## 2. Builder: створення документа

**Що.** `DocumentBuilder` збирає документ викликами `BeginHeading`, `AddParagraph`, `EndHeading`
(або `AddHeading(назва, вміст)`), а `Build()` повертає готовий `Root`.

**Де.** `CharacterSheetBuilder` будує аркуш персонажа за допомогою `DocumentBuilder`
замість ручної навігації `AddHeading` / `Up()` у `TextFactory`.

**Чому.** Побудова дерева вручну вимагала стежити за поточним контейнером, лічильником id та
правилами імен. Білдер ховає цю бухгалтерію, переносить валідацію (`TextRules`) в один спільний клас
і гарантує коректний результат: незакритий розділ призводить до помилки в `Build()`, зайвий `EndHeading()`
дає помилку відразу, а після `Build()` білдер більше не приймає викликів. Готовий корінь можна передати
в `TextFactory.Load(...)`, id продовжаться без колізій.

## 3. Prototype: копіювання піддерев

**Що.** `IPrototype<T>` з методом `Clone(Func<int> nextId)`. Його реалізують `Paragraph` та `Heading`
(глибока копія з усім вмістом). Корінь копіювати не можна (він єдиний у документі).

**Де.** `TextFactory.AddCopy` додає копію в поточний контейнер. Консольна команда:
`cp <назва> [--as <нова назва>]` або `cp --id <id> [--as <нова назва>]`.

**Чому.** Однакові розділи (шаблонні глави, повторювані блоки) зручніше клонувати, ніж створювати
заново елемент за елементом. Класичний `Clone()` розширено джерелом id: кожен елемент у документі
має унікальний id, тому копії отримують нові id (від нього залежать `cd --id`, `rm --id` та збереження).
Копія створюється повністю перед вставкою, тож копіювання предка всередину самого себе безпечне.

## Чого не використано і чому

* **Singleton для кореня.** Документ у системі замінюється через збереження/завантаження (`TextFactory.Load`),
  тому «єдиний корінь» вже забезпечується фасадом `TextFactory`, який володіє одним коренем.
  Глобальний єдиний екземпляр заважав би тестам (спільний стан між тестами) і можливості мати
  кілька документів, а також приховував би залежності.
* **Object Pool.** Елементи тексту легкі й не мають дорогих ресурсів, тому пул не дав би виграшу.
